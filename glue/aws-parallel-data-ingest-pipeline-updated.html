AWS Data Engineering Lab

Parallel Data Ingest Pipeline with AWS Glue, Step Functions, S3, Glue Data Catalog & Athena

A complete, updated implementation guide based on the public-holiday ingestion pattern, expanded with IAM, networking, error handling, observability, Athena output configuration, production considerations, and an implementation blueprint.

1. Architecture overview

The reusable pattern is simple: one parameterized ingestion job is invoked once for each independent item in an input array. Step Functions supplies the item, Glue retrieves and writes the data, and downstream catalog/query services expose it for analytics.

Core design principle: Do not create one Glue job per country. Create one generic job accepting --country_code, then fan out over the country list with a Map state.

2. Why parallel processing?

If 60 independent API calls each take about one second, a sequential design waits for each call in turn. A Map state can overlap independent executions, bounded by a configured concurrency limit. AWS documents Inline Map as limited-concurrency and Distributed Map as the high-concurrency mode for larger workloads. citeturn0search3turn0search2

  • An AWS account and a Region selected for the lab.
  • Permissions to create IAM roles, S3 resources, Glue jobs/crawlers/databases, Step Functions state machines, and Athena workgroups/queries.
  • A browser with access to the AWS Management Console.

  • Internet access for the Glue job if it calls the public Nager.Date endpoint.

S3 read: allow s3:ListBucket on the bucket and s3:GetObject on raw/*.

Catalog permissions: use the crawler/service-role permissions required to create or update the Data Catalog.

6.4 Optional analyst/Athena permissions

Do not give the ingestion roles Athena permissions just because Athena is downstream. Separate query access from pipeline execution access. Analysts generally need Glue Catalog read, Athena query permissions, and access to the Athena results prefix.

Important separation: Step Functions should orchestrate. Glue should ingest. The crawler should catalog. Athena should query. Keeping these permissions separated reduces blast radius.

7. VPC and networking architecture

There are two valid configurations for this lab. Choose deliberately rather than accidentally mixing them.

Option A — Simple labDo not attach the Glue job to a VPC. This is the easiest configuration for a public Nager.Date API and avoids NAT/VPC complexity.
Option B — VPC-enabled labPlace Glue network interfaces in private subnets. Use NAT for public API access and an S3 Gateway VPC endpoint so S3 traffic can remain inside AWS.
Recommended for this expanded hands-on guide: Option B if the goal is to learn AWS networking as well as Glue. Option A if the goal is only to learn Step Functions + Glue orchestration.

├── raw/
│   ├── US.parquet
│   ├── IN.parquet
│   ├── GB.parquet
│   └── ...

Keep ingestion data and Athena results in separate prefixes. This avoids crawler confusion and makes lifecycle policies easier to manage. Athena query results must have an S3 output location configured either in the workgroup or per query. citeturn1search0turn1search6

10. Lab 1 — Create the AWS Glue Python Shell ingestion job

1
Create an S3 bucket

Use a globally unique bucket name. Create raw/ and athena-results/ prefixes. Enable default encryption and block public access.

2
Create the Glue IAM role

Attach the AWS-managed Glue service-role baseline as appropriate, then add narrowly scoped S3 permissions for the lab bucket. Avoid s3:* on * in production.

3
Create a Python Shell job

Select Python Shell. Current AWS documentation lists Python 3.9 for the Python Shell experience; Python 3.6 reached end of life in 2026. citeturn0search0

4
Use a parameterized script

The key contract is --country_code. The job should fail on HTTP errors rather than silently creating a partial output.

import sys
import requests
import boto3
import pandas as pd
from awsglue.utils import getResolvedOptions

args = getResolvedOptions(sys.argv, ["country_code", "output_bucket"])
country = args["country_code"]
bucket = args["output_bucket"]

year = 2026
url = f"https://date.nager.at/api/v3/publicholidays/{year}/{country}"

response = requests.get(url, timeout=30)
response.raise_for_status()

df = pd.DataFrame(response.json())
columns = [c for c in ["date", "name", "countryCode"] if c in df.columns]
df = df[columns]
df["date"] = pd.to_datetime(df["date"], errors="coerce")

local_file = f"/tmp/{country}.parquet"
s3_key = f"raw/{country}.parquet"

df.to_parquet(local_file, engine="pyarrow", index=False)
boto3.client("s3").upload_file(local_file, bucket, s3_key)

print(f"Uploaded s3://{bucket}/{s3_key}")
Why improve the original script? The article's sample uses a fixed 2024 endpoint and prints an HTTP failure without raising an exception. This version makes the year explicit, adds a timeout, raises on HTTP failure, and passes the bucket as a job argument so the same script can be reused across environments. The original workflow uses the same parameterized country-code concept. citeturn0view0

11. Lab 2 — Orchestrate parallel Glue runs with Step Functions

The original tutorial uses an Inline Map over $.country_codes and a concurrency limit of 30. That is a good teaching example for a modest JSON list. AWS also provides Distributed Map for very large datasets/high concurrency. citeturn0view0turn0search2

{
  "country_codes": ["US", "IN", "GB", "DE", "FR"]
}

State machine blueprint

{
  "StartAt": "ForEachCountry",
  "States": {
    "ForEachCountry": {
      "Type": "Map",
      "ItemsPath": "$.country_codes",
      "MaxConcurrency": 30,
      "Iterator": {
        "StartAt": "RunGlue",
        "States": {
          "RunGlue": {
            "Type": "Task",
            "Resource": "arn:aws:states:::glue:startJobRun.sync",
            "Parameters": {
              "JobName": "parallel-holiday-ingest",
              "Arguments": {
                "--country_code.$": "$",
                "--output_bucket": "YOUR_BUCKET"
              }
            },
            "Retry": [
              {
                "ErrorEquals": [
                  "Glue.ConcurrentRunsExceededException",
                  "Glue.AWSGlueException",
                  "States.TaskFailed"
                ],
                "IntervalSeconds": 5,
                "MaxAttempts": 3,
                "BackoffRate": 2
              }
            ],
            "End": true
          }
        }
      },
      "End": true
    }
  }
}

In the optimized Glue integration, the Task resource can use arn:aws:states:::glue:startJobRun.sync; Step Functions waits for the job run to complete. citeturn0search6

Retry design note: Do not blindly retry every error forever. Retry transient service/concurrency failures; route permanent input/API failures to a controlled failure path or record them for later reprocessing.

15. Monitoring and observability

  • Step Functions: inspect execution graph, Map iterations, failed items, and execution history.
  • Glue: inspect job runs, duration, errors and logs.
  • S3: verify expected object count and prefixes.
  • Glue Crawler: verify run status and discovered table/schema.
  • Athena: inspect query history and bytes scanned.
  • CloudWatch: centralize service metrics/logs and create alarms for repeated failures.
Operational improvement: Add a correlation identifier such as an execution ID to logs. For larger pipelines, persist per-country status (success/failure/error message) so one bad item does not hide the state of the whole batch.

19. Three CloudFormation deployment options

Three templates are provided for different teaching and deployment goals. All three use the same logical pipeline: S3 → Glue → Step Functions Map → Glue Crawler/Data Catalog → Athena. The difference is how much infrastructure is automated.

02 — Full simple / no VPC S3, IAM roles, Glue database/job, crawler, Step Functions and Athena workgroup. No VPC, subnet, IGW, NAT or VPC endpoint. Fast classroom lab focused on Glue + Step Functions.

19.4 Recommended teaching sequence

1
Start with Template 3.

Students see the S3 bucket, Glue database and IAM role already available. Then create the Glue job manually and discuss every setting.

2
Create Step Functions manually.

Explain the input array, Map state, ItemsPath, MaxConcurrency, and glue:startJobRun.sync.

3
Create and run the crawler.

Students see how Parquet files become Data Catalog metadata.

4
Query through Athena.

Demonstrate the relationship between S3 objects, Glue Catalog metadata and Athena SQL.

5
Deploy Template 2.

Show how the manually assembled architecture becomes repeatable infrastructure-as-code without adding network complexity.

6
Deploy Template 1.

Finish by adding private networking, NAT and the S3 endpoint, then explain why the network architecture matters.

21. Cleanup

  1. Stop/delete the Step Functions state machine.
  2. Delete the Glue crawler and Glue database/table.
  3. Delete the Glue job.
  4. Delete S3 objects and then the bucket.
  5. Delete the dedicated IAM roles/policies if they are not reused.
  6. Delete the Athena workgroup if created specifically for the lab.
Cost warning: NAT gateways, if added for a VPC version, can incur charges even when traffic is low. Remove them when the lab is complete.

22. Final implementation checklist

  • ☐ S3 bucket created with encryption and public access blocked.
  • ☐ raw/ and athena-results/ prefixes separated.
  • ☐ Glue Python Shell job accepts --country_code and bucket arguments.
  • ☐ Glue job role has only the required S3/log permissions.
  • ☐ Public API connectivity verified.
  • ☐ Step Functions Map reads $.country_codes.
  • ☐ Map concurrency is appropriate for API and Glue limits.
  • ☐ Glue integration uses .sync so downstream steps wait for job completion.
  • ☐ Retry policy covers transient failures without retrying permanent authorization/input failures.
  • ☐ Glue crawler reads only the intended S3 prefix.
  • ☐ Glue Data Catalog table created and schema verified.
  • ☐ Athena query-result location configured.
  • ☐ Athena queries return expected rows.
  • ☐ CloudWatch/Step Functions monitoring checked.
  • ☐ Resources cleaned up after the lab.
