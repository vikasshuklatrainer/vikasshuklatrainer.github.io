Build an event-driven workflow with Amazon EventBridge

Publish a sample OrderPlaced event, filter it with an EventBridge rule, invoke AWS Lambda, and verify processing in CloudWatch Logs—without a database, VPC, NAT Gateway, EC2 instance, or API Gateway.

Amazon EventBridgeAWS LambdaCloudWatch LogsCloudFormation

Lab overview

Scenario: a small order application emits an event when a customer places an order. Amazon EventBridge evaluates the event against a rule. If the event has source lab.orders and detail type OrderPlaced, EventBridge invokes a Lambda function that logs the order details.

Learning objectives
  • Explain event buses, events, rules, patterns, and targets.
  • Publish a custom event to the default event bus.
  • Observe a matched event and Lambda invocation.
  • Prove that non-matching events are filtered out.
What you will create
  • One Lambda function
  • One Lambda execution role and inline policy
  • One EventBridge rule and target
  • One Lambda resource-based invoke permission
  • One CloudWatch log group with 7-day retention
Cost and cleanup: this is a small lab, but AWS usage may incur charges. EventBridge, Lambda, CloudWatch Logs, and CloudFormation pricing/allowances vary by region and account. Delete the stack when finished.

Sample event envelope

{
  "Source": "lab.orders",
  "DetailType": "OrderPlaced",
  "Detail": "{\"orderId\":\"ORD-1001\",\"amount\":149.95,\"currency\":\"USD\"}"
}

EventBridge wraps the submitted values in an event envelope containing fields such as id, source, detail-type, time, and detail. The rule matches on source and detail-type, not on the order amount.

Prerequisites

  • An AWS account and permission to create CloudFormation stacks, IAM roles/policies, Lambda functions, EventBridge rules, and CloudWatch log groups.
  • A region selected in the AWS console. Use the same region for all commands.
  • For CLI steps: AWS CLI v2 configured with credentials and a default region, or pass --region REGION to each command.
IAM note: deployment requires permissions to create the named resources and pass the Lambda execution role to Lambda. In a managed training account, an administrator may need to grant these permissions.

Choose a prefix starting with a letter and containing only letters, numbers, and hyphens. Example: eblab. Keep it 3–20 characters. The prefix is applied to all explicitly named resources in this template.

1Deploy with CloudFormation (recommended)

  1. Download eventbridge-order-lab.yaml using the button at the top of this page.
  2. Open the AWS CloudFormation console in your selected region and choose Create stack → With new resources (standard).
  3. Choose Upload a template file, upload the YAML file, and continue.
  4. For stack name, enter EventBridge-Order-Lab (or a name your account permits).
  5. For ResourcePrefix, enter a value such as eblab. Review the generated resource names below before creating the stack.
  6. Continue through the remaining pages. Acknowledge IAM resource creation if prompted, then choose Submit.
  7. Wait for stack status CREATE_COMPLETE. On the Outputs tab, note the Lambda function name, rule name, and log group name.

The template uses the default event bus, so it does not create a custom event bus. The rule's target is the Lambda function, and a scoped Lambda permission allows only this EventBridge rule to invoke it.

2Deploy with AWS CLI (optional alternative)

Use this instead of the console deployment, not in addition to it. Run from the folder containing the template. Replace the region and prefix as needed.

aws cloudformation deploy \
  --template-file eventbridge-order-lab.yaml \
  --stack-name EventBridge-Order-Lab \
  --parameter-overrides ResourcePrefix=eblab \
  --capabilities CAPABILITY_NAMED_IAM \
  --region us-east-1

Check stack status and outputs:

aws cloudformation describe-stacks \
  --stack-name EventBridge-Order-Lab \
  --query "Stacks[0].{Status:StackStatus,Outputs:Outputs}" \
  --output table \
  --region us-east-1

For the rest of the lab, replace us-east-1 with your chosen region if different.

3Publish a matching event

Use the AWS CLI to publish one custom event to the default event bus. This command is a simulated order application publishing an event.

aws events put-events \
  --entries '[{
    "Source":"lab.orders",
    "DetailType":"OrderPlaced",
    "EventBusName":"default",
    "Detail":"{\"orderId\":\"ORD-1001\",\"amount\":149.95,\"currency\":\"USD\"}"
  }]' \
  --region us-east-1

A successful response contains FailedEntryCount: 0 and an event ID. EventBridge delivery is asynchronous, so allow a short interval before checking Lambda logs.

Shell note: the example uses Bash-compatible quoting. In PowerShell, use a here-string or carefully escape JSON quotes. See the PowerShell example below.

PowerShell version

$entry = @{
  Source = "lab.orders"
  DetailType = "OrderPlaced"
  EventBusName = "default"
  Detail = '{"orderId":"ORD-1001","amount":149.95,"currency":"USD"}'
} | ConvertTo-Json -Compress

aws events put-events --entries "[$entry]" --region us-east-1

Repeat with a different order ID, for example ORD-1002, to generate another invocation.

4Validate the result in CloudWatch Logs

  1. Open the CloudWatch console in the same region.
  2. Choose Logs → Log groups.
  3. Open /aws/lambda/eblab-EventProcessor (substitute your prefix).
  4. Open the newest log stream, corresponding to the recent invocation.
  5. Find EVENT_RECEIVED and ORDER_PROCESSED. Verify the order ID, amount, currency, source, and detail type.

Expected log content (illustrative)

ORDER_PROCESSED {
  "message": "OrderPlaced event processed",
  "source": "lab.orders",
  "detailType": "OrderPlaced",
  "orderId": "ORD-1001",
  "amount": 149.95,
  "currency": "USD"
}

The exact timestamp and EventBridge event ID will differ. The Lambda handler writes the complete received event and a concise processing summary to the log stream.

Optional CLI validation

aws logs tail /aws/lambda/eblab-EventProcessor \
  --since 10m \
  --follow \
  --region us-east-1
Success criteria: the put-events response has zero failed entries, a recent Lambda log stream exists, and the logs contain the matching order ID.

5Test rule filtering with a non-matching event

Now publish an event with the wrong source. It should be accepted by the event bus but not match this rule, so the target Lambda should not be invoked by this event.

aws events put-events \
  --entries '[{
    "Source":"lab.inventory",
    "DetailType":"OrderPlaced",
    "EventBusName":"default",
    "Detail":"{\"orderId\":\"ORD-NEG-01\",\"amount\":12.00,\"currency\":\"USD\"}"
  }]' \
  --region us-east-1

Wait briefly and inspect the log group. You should not see a new ORDER_PROCESSED record for ORD-NEG-01. Use a unique negative-test ID and compare log timestamps so previous invocations do not confuse the result.

Why? The event pattern requires source = lab.orders and detail-type = OrderPlaced. Both conditions must match. EventBridge does not invoke the target for this event.

Important: put-events returning zero failed entries means the event was accepted by EventBridge; it does not mean a rule matched or that a target ran.

6Explore the configuration in the AWS console

  1. Open Amazon EventBridge → Rules and select eblab-OrderPlacedRule.
  2. Inspect the event bus (default), status (enabled), event pattern, and target.
  3. Confirm the pattern includes the source lab.orders and detail type OrderPlaced.
  4. Open the Lambda console and select eblab-EventProcessor. Inspect the Python code and configuration.
  5. Open the Lambda function's Monitor tab and follow the CloudWatch Logs link.
  6. In CloudFormation, inspect the stack's Resources and Outputs tabs to connect logical resources to deployed names.

IAM and security notes

  • Lambda trust policy: allows the lambda.amazonaws.com service to assume the execution role.
  • Lambda logging policy: permits only logs:CreateLogStream and logs:PutLogEvents on the function's log group ARN. The log group is created by CloudFormation and retained for seven days.
  • EventBridge-to-Lambda permission: the Lambda resource policy allows principal events.amazonaws.com to invoke the function, scoped to this rule's ARN.
  • No broad application permissions: the function does not access S3, databases, secrets, or other AWS services.
  • Production considerations: validate event schemas, avoid logging sensitive data, design idempotent handlers, consider retries/dead-letter queues for important workloads, and add monitoring/alarms appropriate to business impact.
This lab intentionally uses an inline CloudFormation Lambda source package for simplicity. For production, use version-controlled deployment artifacts, reviewed IAM policies, operational alarms, and a release process.

Cost considerations

  • No always-on compute is created. Lambda runs only when invoked.
  • EventBridge custom events and Lambda invocations are usage-based; CloudWatch Logs incurs ingestion/storage charges. Free-tier eligibility and prices vary.
  • The log group has seven-day retention to limit stored logs.
  • Use a small number of test events and delete the stack when done. Check the current AWS pricing pages for your region before running labs at scale.

Cleanup — delete all lab resources

  1. Open CloudFormation in the deployment region.
  2. Select EventBridge-Order-Lab (or your chosen stack name).
  3. Choose Delete and confirm.
  4. Wait until the stack disappears or reaches DELETE_COMPLETE.
  5. Verify the Lambda function, EventBridge rule, execution role, and log group have been removed.
aws cloudformation delete-stack \
  --stack-name EventBridge-Order-Lab \
  --region us-east-1

aws cloudformation wait stack-delete-complete \
  --stack-name EventBridge-Order-Lab \
  --region us-east-1

Do not manually delete resources before deleting the stack unless you understand CloudFormation drift. This template creates no custom event bus or other persistent data store.

Learner challenge

Knowledge check

  1. Which two fields does the rule match?
  2. Why does the Lambda function need an execution role?
  3. Why does EventBridge need permission to invoke Lambda?
  4. What does FailedEntryCount: 0 prove—and what does it not prove?
Show suggested answers
  1. source and detail-type.
  2. To define the AWS actions Lambda code is allowed to perform; here it can write logs.
  3. Lambda uses a resource-based permission to authorize the EventBridge service principal, scoped to the rule ARN.
  4. It proves the event entry was accepted by the EventBridge API; it does not prove that a rule matched or the target was invoked.
