Build the Smallest Practical Workflow with Step Functions + 3 Lambda Functions

01 • Goal

What you will build

The workflow processes a small order using three independent Lambda functions. Step Functions passes each function's output to the next state, making the execution visible as a graph.

ResourceCountPurpose
AWS Step Functions state machine1Orchestrates the three steps and tracks execution status.
AWS Lambda functions3Validate input, calculate amount, and prepare a response.
Lambda execution IAM role1 shared roleAllows all three functions to write logs to CloudWatch Logs.
Step Functions execution IAM role1Allows the state machine to invoke only these three Lambda functions.
CloudWatch log groupsCreated as neededCapture Lambda function logs; Step Functions execution history is available in the console.
Minimal design decision: use one shared Lambda execution role for the three demo functions. In production, separate roles per function can provide tighter isolation. No Lambda function needs permission to call another function, and no Lambda resource-based policy is needed for this same-account pattern when the Step Functions role has lambda:InvokeFunction on the function ARNs.
Cost guardrail: this lab uses no always-on compute, VPC, NAT Gateway, database, or load balancer. Lambda and Step Functions usage is request-based, but AWS charges can still apply depending on account, Region, free-tier eligibility, logging, and total usage. Delete the resources after the lab.

Permissions flow

  • Step Functions service principal (states.amazonaws.com) assumes the state machine execution role.
  • The state machine execution role has lambda:InvokeFunction permission limited to the three function ARNs.
  • Lambda service principal (lambda.amazonaws.com) assumes the shared Lambda execution role.
  • The Lambda execution role has CloudWatch Logs permissions via AWSLambdaBasicExecutionRole. The functions do not access any other AWS service.

04 • Security

Create the IAM roles and policies

Create the roles before the functions so you can explicitly select the correct execution role. There are two roles because the workflow orchestrator and the function code are separate security principals.

4.1 Create the Lambda execution role

  1. Open the IAM console → Roles → Create role.
  2. For trusted entity type, choose AWS service; choose Lambda as the use case.
  3. Attach the AWS managed policy AWSLambdaBasicExecutionRole. This grants the basic permissions needed to create log streams and write function logs to CloudWatch Logs.
  4. Set role name to <ResourcePrefix>-LambdaExecutionRole, review, and create the role.
  5. Open the role and verify its trust relationship trusts lambda.amazonaws.com.

Trust policy (reference): the Lambda console creates this when you choose Lambda as the trusted service.

{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Principal": { "Service": "lambda.amazonaws.com" },
      "Action": "sts:AssumeRole"
    }
  ]
}

Permissions attached: AWS managed policy arn:aws:iam::aws:policy/service-role/AWSLambdaBasicExecutionRole. It provides CloudWatch Logs write permissions. Do not attach permissions for S3, databases, or Step Functions because these functions do not need them.

4.2 Create the Step Functions execution role

Use the same ResourcePrefix value for all three Lambda function names, all three ARNs in the Step Functions role policy, and the state machine. The manual steps and CloudFormation template now use the same naming pattern.

  1. In IAM → Roles → Create role, select AWS service and choose Step Functions.
  2. Proceed through permissions without attaching broad policies. Create role named <ResourcePrefix>-StepFunctionsExecutionRole.
  3. Open the role and add an inline policy with the JSON below. Replace REGION and ACCOUNT_ID with your actual Region and 12-digit AWS account ID, and keep the three function names exact.
  4. Name the policy <ResourcePrefix>-InvokeLabFunctions and save.

Trust policy: when creating a Step Functions role from the console, AWS creates a trust relationship for Step Functions. Verify that it permits the Step Functions service principal, typically states.amazonaws.com.

{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Principal": { "Service": "states.amazonaws.com" },
      "Action": "sts:AssumeRole"
    }
  ]
}

Inline permissions policy:

{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "InvokeOnlyThisLabFunctions",
      "Effect": "Allow",
      "Action": "lambda:InvokeFunction",
      "Resource": [
        "arn:aws:lambda:REGION:ACCOUNT_ID:function:<ResourcePrefix>-ValidateOrder",
        "arn:aws:lambda:REGION:ACCOUNT_ID:function:<ResourcePrefix>-CalculateTotal",
        "arn:aws:lambda:REGION:ACCOUNT_ID:function:<ResourcePrefix>-FormatResponse"
      ]
    }
  ]
}
Important: replace the placeholders before saving. Example ARN shape: arn:aws:lambda:ap-south-1:123456789012:function:<ResourcePrefix>-ValidateOrder. Do not paste the example account ID into your own policy. If you later invoke a qualified version or alias ARN, update the policy to match that qualified ARN.

05 • Function 1

Create Lambda 1 — ValidateOrder

  1. Open Lambda → Functions → Create function → Author from scratch.
  2. Function name: <ResourcePrefix>-ValidateOrder.
  3. Runtime: select a currently supported Python 3.x runtime available in your Region.
  4. Under permissions, expand the default execution role options and select Use an existing role; choose <ResourcePrefix>-LambdaExecutionRole.
  5. Create the function. In the Code tab, replace the sample code with the code below and choose Deploy.
import json
import logging

logger = logging.getLogger()
logger.setLevel(logging.INFO)

def lambda_handler(event, context):
    logger.info("ValidateOrder received: %s", json.dumps(event))

    order_id = event.get("orderId")
    quantity = event.get("quantity")
    unit_price = event.get("unitPrice")

    if not order_id:
        raise ValueError("orderId is required")
    if not isinstance(quantity, (int, float)) or isinstance(quantity, bool) or quantity <= 0:
        raise ValueError("quantity must be a positive number")
    if not isinstance(unit_price, (int, float)) or isinstance(unit_price, bool) or unit_price < 0:
        raise ValueError("unitPrice must be a non-negative number")

    result = {
        "orderId": str(order_id),
        "quantity": quantity,
        "unitPrice": unit_price,
        "validated": True
    }
    logger.info("Validation successful for orderId=%s", order_id)
    return result

Test the function directly

Create a test event named ValidOrder with this JSON, then choose Test.

{
  "orderId": "ORD-1001",
  "quantity": 3,
  "unitPrice": 12.5
}

Expected result includes "validated": true, "quantity": 3, and "unitPrice": 12.5.

06 • Function 2

Create Lambda 2 — CalculateTotal

  1. Create another function named <ResourcePrefix>-CalculateTotal, using the same Python runtime and the existing role <ResourcePrefix>-LambdaExecutionRole.
  2. Replace the code, choose Deploy, and test with the same valid order input.
import json
import logging

logger = logging.getLogger()
logger.setLevel(logging.INFO)

def lambda_handler(event, context):
    logger.info("CalculateTotal received: %s", json.dumps(event))

    quantity = event["quantity"]
    unit_price = event["unitPrice"]
    total = round(quantity * unit_price, 2)

    result = {
        **event,
        "total": total
    }
    logger.info("Calculated total=%s for orderId=%s", total, event["orderId"])
    return result

Expected result includes "total": 37.5. This function intentionally relies on Lambda 1 to validate the required fields; the workflow is a simple teaching example, not a production order system.

07 • Function 3

Create Lambda 3 — FormatResponse

  1. Create a third function named <ResourcePrefix>-FormatResponse, with the same runtime and existing shared role.
  2. Replace the code and choose Deploy.
import json
import logging

logger = logging.getLogger()
logger.setLevel(logging.INFO)

def lambda_handler(event, context):

All three functions should now be deployed. Confirm their function names and execution role under each function's Configuration → Permissions page.

08 • Orchestration

Create the Step Functions state machine

  1. Open Step Functions → State machines → Create state machine.
  2. Choose Write your workflow in code / create from blank (console wording may vary), and select Standard workflow type for a clear execution-history demonstration.
  3. Name it <ResourcePrefix>-OrderWorkflow.
  4. Paste the Amazon States Language definition below. Replace the three Lambda ARNs with the exact ARNs shown on your Lambda function pages.
  5. For execution role, choose Choose an existing role and select <ResourcePrefix>-StepFunctionsExecutionRole.
  6. Validate the definition, create the state machine, and resolve any policy/ARN validation errors before running it.
{
  "Comment": "Minimal order processing workflow with three Lambda functions",
  "StartAt": "ValidateOrder",
  "States": {
    "ValidateOrder": {
      "Type": "Task",
      "Resource": "arn:aws:lambda:REGION:ACCOUNT_ID:function:<ResourcePrefix>-ValidateOrder",
      "Next": "CalculateTotal"
    },
    "CalculateTotal": {
      "Type": "Task",
      "Resource": "arn:aws:lambda:REGION:ACCOUNT_ID:function:<ResourcePrefix>-CalculateTotal",
      "Next": "FormatResponse"
    },
    "FormatResponse": {
      "Type": "Task",
      "Resource": "arn:aws:lambda:REGION:ACCOUNT_ID:function:<ResourcePrefix>-FormatResponse",
      "End": true
    }
  }
}
Why this integration style? This definition uses the direct Lambda function ARN as a Task resource. It keeps the workflow definition short and passes the Lambda return value to the next state. Step Functions also supports the optimized arn:aws:states:::lambda:invoke integration, which exposes the Lambda response envelope and offers additional integration features. For this minimal lab, direct invocation keeps the data flow easy to inspect.

Important ARN replacement

For example, if your Region is ap-south-1 and your account ID is 123456789012, the first ARN would look like this:

arn:aws:lambda:ap-south-1:123456789012:function:<ResourcePrefix>-ValidateOrder

Use your real account ID and Region. The state machine and Lambda functions should be in the same account and Region for this lab.

09 • Validation

Run the workflow and inspect the output

  1. In Step Functions, open <ResourcePrefix>-OrderWorkflow and choose Start execution.
  2. Use execution input:
{
  "orderId": "ORD-1001",
  "quantity": 3,
  "unitPrice": 12.5
}
  1. Choose Start execution. Wait for the status to become Succeeded.
  2. In the execution graph, select each state and inspect its input/output. Verify that Lambda 1 adds validated, Lambda 2 adds total, and Lambda 3 returns the final response.
  3. Check the execution output. The total should be 37.5.

Validation checklist

  • All three states show success in the execution graph.
  • The first state's output contains "validated": true.
  • The second state's output contains "total": 37.5.
  • The final output contains "status": "SUCCESS" and the expected message.
  • The state machine execution role contains only the three Lambda invoke permissions required for this workflow.
10 • Negative test

Demonstrate a failed execution

This test demonstrates that an unhandled exception in a Lambda Task causes the Step Functions state to fail.

  1. Start another execution with the following invalid input (quantity is missing):
{
  "orderId": "ORD-1002",
  "unitPrice": 12.5
}
  1. The ValidateOrder function should raise ValueError because quantity is missing/invalid.
  2. The execution should fail at ValidateOrder; the later two Lambda functions should not run.
  3. Select the failed state in the execution graph and inspect the error name and cause.
  4. Open the Lambda function's Monitor tab or CloudWatch Logs and find the invocation's exception and log messages.
Expected for this first version: the workflow fails rather than catching the exception. A later exercise can add Retry and Catch states to teach retries and controlled error handling. Do not add retries to validation errors in production without a reason; invalid input usually will not become valid on retry.
11 • Observability

Where to see execution history and logs

Step Functions execution details

  1. Open Step Functions → State machines → <ResourcePrefix>-OrderWorkflow → Executions.
  2. Choose the execution ID. Use the graph and event history to view state transitions, input/output, duration, and failure details.

Lambda logs in CloudWatch

  1. Open CloudWatch → Logs → Log groups.
  2. Find /aws/lambda/<ResourcePrefix>-ValidateOrder, /aws/lambda/<ResourcePrefix>-CalculateTotal, or /aws/lambda/<ResourcePrefix>-FormatResponse.
  3. Open the newest log stream and inspect the custom logger.info messages. For the negative test, inspect the exception/traceback in the ValidateOrder log stream.
Lambda log groups may appear after the first invocation. This lab does not enable Step Functions CloudWatch Logs delivery; execution details are available in the Step Functions console. Enabling Step Functions logging is optional and would require additional permissions and incur standard CloudWatch Logs charges.

09 • Infrastructure as Code

Deploy the entire lab with CloudFormation

The standalone CloudFormation template creates the same three-Lambda workflow, the two IAM roles and their least-privilege permissions, explicit CloudWatch Logs groups with seven-day retention, and the Step Functions state machine. Lambda code is embedded in the template, so no ZIP upload or S3 bucket is needed.

ResourcePrefix parameter: during stack creation, CloudFormation asks for ResourcePrefix. That prefix is applied to all named resources created by this stack, including the Lambda functions, IAM role names, state machine name, and Lambda log group names. Resources are also tagged with the prefix where supported.

9.1 Download the template

Download the CloudFormation YAML template. Keep the YAML file and this HTML guide in the same folder if you want the download link to work locally.

9.2 Deploy through the AWS Console

  1. Open AWS CloudFormation → Stacks → Create stack → With new resources (standard).
  2. Choose Upload a template file and upload aws_step_functions_minimal_lambda_lab.yaml.
  3. Choose a stack name, for example sfn-mini-demo-stack.
  4. On the Parameters page, enter a ResourcePrefix, for example abhi-sfn-demo. It must start with a letter and contain only letters, numbers, or hyphens; length is 3–20 characters. Choose a prefix that is unique enough to avoid naming collisions in your account.
  5. Continue through the remaining pages. Acknowledge IAM resource creation if prompted, review the template, and submit.
  6. Wait until the stack status is CREATE_COMPLETE. If creation fails, open the stack's Events tab and inspect the first failed resource.
  7. Open the stack's Outputs tab and copy the StateMachineArn or open the state machine from Step Functions.

9.3 Run the deployed workflow

In Step Functions, open the state machine named <ResourcePrefix>-OrderWorkflow and choose Start execution with this input:

{
  "orderId": "ORD-1001",
  "quantity": 3,
  "unitPrice": 12.5
}

Expected output includes "total": 37.5 and "status": "SUCCESS". To test failure handling, start another execution with quantity missing or set to zero; the ValidateOrder task should fail.

9.5 What the template provisions

  • One shared Lambda execution role trusted by lambda.amazonaws.com, with AWSLambdaBasicExecutionRole for CloudWatch Logs.
  • One Step Functions role trusted by states.amazonaws.com, with lambda:InvokeFunction limited to the three functions in this stack.
  • Three Python Lambda functions (128 MB memory, 10-second timeout), with code included inline.
  • Three explicit CloudWatch log groups with seven-day retention, to avoid indefinite retention for this classroom demo.
  • One Standard Step Functions state machine that calls the three functions in sequence.
IAM note: CloudFormation must be run by a deployment identity that is permitted to create IAM roles and attach the referenced managed policy. This template intentionally does not grant the Lambda functions permissions to invoke one another or start Step Functions executions.

  4. If deletion fails, inspect the Events tab. Do not manually delete shared resources that were not created by this stack.
Do not create the same named resources manually before deploying this template. Explicit function, role, state-machine, and log-group names must be unique within their relevant AWS scope. If a name already exists, choose another ResourcePrefix.
12 • Cost

Cost and resource footprint

This is intentionally a tiny, request-driven demo. It uses three short Lambda functions and one Standard Step Functions state machine. There is no always-on infrastructure.

  • Lambda: charged based on requests and compute duration, subject to current regional pricing and any applicable free tier.
  • Step Functions Standard: charged based on state transitions. This successful path uses three Task states; failed executions and additional states can change transition counts.
  • CloudWatch Logs: log ingestion and storage can incur charges. Keep the lab short and clean up log groups if you do not need them.
  • IAM: IAM roles and policies do not generally have a separate charge.
Do not treat “small” as “guaranteed free.” Check the current AWS pricing pages for your Region, account plan, and usage. If the lab is run repeatedly by a class, set an AWS Budget or use a controlled training account.

Delete all lab resources

Clean up after capturing any screenshots or teaching notes. Deleting the state machine and functions does not always remove CloudWatch log groups automatically.

  1. In Step Functions, open <ResourcePrefix>-OrderWorkflow and delete the state machine. Confirm the deletion prompt.
  2. In Lambda, delete <ResourcePrefix>-ValidateOrder, <ResourcePrefix>-CalculateTotal, and <ResourcePrefix>-FormatResponse.
  3. In CloudWatch → Logs → Log groups, delete the three log groups matching the /aws/lambda/<ResourcePrefix>- prefix if you no longer need their history.
  4. In IAM, delete the inline policy <ResourcePrefix>-InvokeLabFunctions from <ResourcePrefix>-StepFunctionsExecutionRole, then delete that role.
  5. In IAM, detach AWSLambdaBasicExecutionRole from <ResourcePrefix>-LambdaExecutionRole, then delete that role.
  6. Check that no other resources were created accidentally during the lab.
Delete only the resources created for this lab. Do not delete shared IAM roles, policies, or log groups used by other workloads. If you selected auto-generated roles instead of the named roles in this guide, identify their attached resources carefully before removing them.
14 • Student exercises

Exercises and expected learning

  1. Change the input: set quantity to 5 and unitPrice to 9.99. Predict the total, execute, and verify.
  2. Trigger validation failure: set quantity to 0. Identify the failing state and compare its event history with a successful execution.
  3. Add a decision: add a Choice state after validation to route orders with total greater than 100 to a separate result path. (Hint: calculate the total before evaluating it, or add the decision after CalculateTotal.)
  4. Add controlled error handling: use a Catch field to route validation errors to a Fail or Pass state that returns a readable error message. Ensure the error path does not continue to CalculateTotal.
  5. Apply least privilege: explain why the state machine role needs invoke permissions while the Lambda role does not.
  6. Production design discussion: identify why separate execution roles per function, input schema validation, idempotency, alarms, and data protection may be needed in a real application.

Completion criteria

  • Student created both IAM roles and reviewed the trust relationships.
  • Student attached only required permissions to the roles.
  • All three Lambda functions execute successfully in the state machine.
  • Student can explain input/output handoff between the Task states.
  • Student successfully demonstrates and diagnoses one failed execution.
  • All lab resources are removed.
