AWS DMS: S3 → RDS PostgreSQL

Deployment, configuration, CSV preparation, migration execution and troubleshooting guide for the CloudFormation template dms-rds-postgres-fixed-v5-crlf.yaml.

Working configuration: CSV CRLF IgnoreHeaderRows=1 PostgreSQL 16 DMS dms.t3.medium

1. What this template creates

S3 CSV → AWS DMS Replication Instance → PostgreSQL Target Endpoint → Amazon RDS PostgreSQL
VPC10.0.0.0/16 by default, with two public subnets.
S3Encrypted private source bucket with DMS read access.
RDS PostgreSQLPostgreSQL 16, db.t3.micro, publicly accessible.
AWS DMSdms.t3.medium replication instance and replication subnet group.
DMS SourceS3 CSV endpoint with CRLF row delimiter.
DMS TargetPostgreSQL endpoint using SSL.

2. Working Architecture

The following SVG shows the actual working data path documented in this guide: the CSV is placed in Amazon S3, AWS DMS reads the file through the S3 source endpoint, the DMS replication instance processes it, and the PostgreSQL target endpoint loads public.employees into Amazon RDS for PostgreSQL.

Working configuration: CsvDelimiter=,, CsvRowDelimiter=\r\n, DataFormat=csv, and IgnoreHeaderRows=1. The CRLF row delimiter is important for the Windows-formatted CSV used in this demo.

2. Prerequisites

  1. AWS account with permission to create CloudFormation, VPC, IAM, S3, RDS and DMS resources.
  2. AWS CLI configured if deploying from a terminal.
  3. CloudFormation capability CAPABILITY_NAMED_IAM.
  4. The DMS service role dms-vpc-role must either already exist or be created by the stack using CreateDmsVpcRole=true.
  5. For this demo, allow PostgreSQL access to the RDS security group. The template currently opens TCP/5432 to 0.0.0.0/0; this is acceptable only for a controlled lab/demo and should be restricted for production.

4. Deploy the CloudFormation stack

Save the template as dms-rds-postgres-fixed-v5-crlf.yaml.

Example AWS CLI deployment:

aws cloudformation deploy \
  --stack-name tink-dms-demo \
  --template-file dms-rds-postgres-fixed-v5-crlf.yaml \
  --parameter-overrides ResourcePrefix=tink \
  --capabilities CAPABILITY_NAMED_IAM

Alternatively use CloudFormation → Create stack → With new resources → Upload the template.

Role-name conflict: if CloudFormation reports that dms-vpc-role already exists, keep CreateDmsVpcRole=false. The template then uses the existing role rather than trying to create another fixed-name role.

During troubleshooting, hired_on was temporarily changed to STRING(10) to isolate S3/DMS date parsing. The final working fix was the CRLF row delimiter. If your deployed template still contains DATE for hired_on, use valid ISO dates in the CSV and the correct CRLF row delimiter.

9. PostgreSQL target

The target database is appdb. The DMS target endpoint connects using PostgreSQL SSL:

sslmode=require

Expected target table structure for the demonstration:

CREATE TABLE public.employees
(
    id BIGINT PRIMARY KEY,
    name VARCHAR(100),
    salary NUMERIC(10,2),
    hired_on DATE
);

Verify the table:

SELECT column_name, data_type
FROM information_schema.columns
WHERE table_schema = 'public'
  AND table_name = 'employees'
ORDER BY ordinal_position;

10. Run the DMS migration

  1. Open AWS DMS → Database migration tasks.
  2. Select the task created by the stack.
  3. Make sure the source endpoint is the S3 endpoint and the target endpoint is PostgreSQL.
  4. For a clean demo run, use Start fresh.
  5. Monitor the table public.employees.

A successful run should show 20 rows received and no table error.

11. Verify the migration

Connect to the RDS database and run:

SELECT COUNT(*) FROM public.employees;

SELECT *
FROM public.employees
ORDER BY id;

13. Important template consistency check

Before using this template for a fresh deployment, verify the database password values. The template file currently contains admin123434 for the RDS MasterUserPassword, while the DMS PostgreSQL target endpoint contains admin1234. These must match for a fresh stack. The working environment used admin1234.

For a clean deployment, make both values the same before creating the stack. Also avoid hard-coded passwords in production; use AWS Secrets Manager or another secure secret mechanism.

14. Resource cleanup

This template creates billable AWS resources, especially RDS and DMS. For a lab, delete the CloudFormation stack after the exercise:

aws cloudformation delete-stack --stack-name tink-dms-demo

Confirm the stack has been deleted and that the RDS instance, DMS replication instance, S3 bucket contents, and associated resources no longer incur charges.

  All resources are named with the prefix you supply.

Console Walkthrough — Create Endpoints and Run a Full Load

This section demonstrates the same S3 → AWS DMS → PostgreSQL flow manually through the AWS DMS console. It assumes that the CSV file already exists in S3, the target PostgreSQL database/table is available, and the required IAM role for DMS S3 access already exists. No CloudFormation is required for these steps.

Terminology note: For an S3 source endpoint, AWS DMS needs an IAM role that allows DMS to read the S3 bucket. If by “instance profile” you mean an EC2 instance profile, that is not the credential mechanism used by the DMS S3 endpoint. Use the DMS S3 access IAM role and its ARN.

Lab flow

Prerequisites

  1. Open the AWS console in the region where the DMS replication instance and database are located.
  2. Confirm the CSV is uploaded to the S3 bucket. For this demonstration the expected object is data/public/employees/LOAD00000001.csv.
  3. Confirm the DMS replication instance is Available.
  4. Confirm the target PostgreSQL database is reachable from the DMS replication instance on TCP 5432.
  5. Have the DMS S3 access role ARN available. Example: arn:aws:iam::<account-id>:role/<dms-s3-access-role>.
  6. For the working CSV demonstration, use Windows CRLF rows and configure the S3 endpoint with CsvRowDelimiter = \r\n.

1. Create the Source Endpoint — Amazon S3

  1. Open AWS DMS in the AWS console.
  2. From the left navigation, choose Endpoints.
  3. Choose Create endpoint.
  4. For Endpoint type, select Source endpoint.
  5. Enter an endpoint identifier, for example s3-employees-source.
  6. For Source engine, select Amazon S3.
  7. Under the S3 settings, enter the Bucket name.
  8. Enter the bucket folder/prefix containing the data. For this lab, use data if the complete object path is data/public/employees/LOAD00000001.csv.
  9. For Service access role ARN, enter the IAM role ARN that allows AWS DMS to access the S3 bucket.
  10. Set the CSV options to match the source file:
    • Data format: CSV
    • Column delimiter: comma (,)
    • Row delimiter: CRLF (\r\n) for the working Windows CSV used in this lab
    • Ignore header rows: 1
  11. For this demonstration, define the source table using an external table definition. This JSON tells AWS DMS how the CSV file maps to the logical source table and its columns.

2. Create the Target Endpoint — PostgreSQL

  1. Stay in AWS DMS → Endpoints.
  2. Choose Create endpoint.
  3. For Endpoint type, select Target endpoint.
  4. Enter an endpoint identifier, for example postgres-employees-target.
  5. For Target engine, select PostgreSQL.
  6. Enter the PostgreSQL server/RDS endpoint DNS name.
  7. Set Port to 5432.
  8. Enter the database name, for example appdb.
  9. Enter the PostgreSQL username and password.
  10. If the target requires encrypted connections, set the SSL mode to require, matching the working demonstration.
  11. Choose Create endpoint.

3. Test Both Endpoints

Before creating the migration task, validate connectivity.

  1. In AWS DMS → Endpoints, select the S3 source endpoint.
  2. Choose Actions → Test connection.
  3. Select the existing DMS replication instance.
  4. Run the test and wait for successful status.
  5. Repeat the same process for the PostgreSQL target endpoint.
  6. Do not proceed to the task until both endpoint tests are successful.
If the target connection fails: verify the RDS security group allows TCP 5432 from the DMS replication instance/network, verify the hostname and database name, and verify the PostgreSQL credentials and SSL requirement.

4. Create the Replication Task — Full Load

  1. In AWS DMS, open Database migration tasks from the left navigation.
  2. Choose Create task.
  3. Enter a task identifier, for example s3-to-postgres-full-load.
  4. Select the existing replication instance.
  5. For Source database endpoint, select the S3 source endpoint created in Step 1.
  6. For Target database endpoint, select the PostgreSQL target endpoint created in Step 2.
  7. For Migration type, select Migrate existing data / Full load as presented by the console.
  8. Under Table mappings, choose the guided/selection rule option and include the source schema/table represented by the S3 external table definition. For this lab the logical table is public.employees.
  9. Under task settings, keep the default settings initially for the demonstration unless a specific target preparation mode is required.
  10. Review the configuration.
  11. Choose Create task.

5. Start the Full-Load Task

  1. Open the newly created task.
  2. Choose Actions → Start (or the equivalent Start/Resume action shown by the console).
  3. Select the option to start the task from the beginning if prompted.
  4. Wait for the task status to move from Starting to Running and then Load complete/Stopped, depending on the console presentation.
  5. Open the task's Table statistics to verify that rows were loaded.

6. Verify the Result in PostgreSQL

Connect to the target database and run:

SELECT COUNT(*) FROM public.employees;

FROM public.employees
ORDER BY id;
