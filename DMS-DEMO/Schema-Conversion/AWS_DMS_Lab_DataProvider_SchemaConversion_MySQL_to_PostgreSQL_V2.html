This lab deliberately demonstrates the schema-conversion work rather than treating it as a black box.

1. Lab purpose

This Version 2 lab is designed so that a learner can see, inspect, compare, modify and validate the result of AWS DMS Schema Conversion.

Scope: MySQL is the source and PostgreSQL is the target. No Oracle is used anywhere in this lab.

AWS DMS Schema Conversion converts database schema and supported database code objects; it does not migrate the actual table data. Data movement is a separate AWS DMS data-migration activity. The workflow used here follows the AWS documented pattern: create data providers and an instance profile, create a migration project, assess, convert, review/edit, and apply or export the converted code.

AWS reference: DMS Schema Conversion overview and workflow.

If CloudFormation reports InsufficientDBInstanceCapacityFault: the selected RDS instance class/storage combination does not currently have sufficient capacity in the available Availability Zones for the request. This is an AWS infrastructure-capacity issue, not a DMS Schema Conversion issue.

Use the updated CloudFormation template

For this lab, use:

AWS_DMS_SchemaConversion_Lab_V2_Demo_No_AZ.yaml

The revised template makes three changes:

  1. No AvailabilityZone parameters are required from the learner.
  2. The VPC creates three public subnets using the first three AZs returned automatically by AWS.
  3. The RDS DBInstance resources do not specify an AvailabilityZone; RDS can choose the placement.

Why three subnets? The RDS DB subnet group still spans multiple Availability Zones. The learner does not have to select the AZs manually, and RDS has more AZ choices when placing the single-AZ lab instance. Creating additional subnets does not itself incur an hourly charge.
Important: This does not guarantee capacity. AWS can still reject a particular instance class/storage combination if capacity is unavailable. If that happens, change the CloudFormation parameter MySQLInstanceClass or PostgreSQLInstanceClass to db.t3.micro (the default in the revised template), or try another Region.

Do not try to remove AZs from the DB subnet group completely

RDS DB subnet groups are designed around subnets in multiple Availability Zones. Therefore, “without Availability Zone” should mean without hard-coding a specific AZ for the DB instance, not “create an RDS DB subnet group with no AZs.”

6. Step 1 — Prepare the MySQL source database

Create a small but intentionally interesting schema. The goal is not merely to move four simple tables; it is to give Schema Conversion something observable to analyze.

6.1 Create the database

CREATE DATABASE saleslab;
USE saleslab;

6.2 Create customers

CREATE TABLE customers (
    customer_id INT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
    customer_name VARCHAR(100) NOT NULL,
    email VARCHAR(150),
    credit_limit DECIMAL(12,2),
    is_active TINYINT(1) DEFAULT 1,
    created_at DATETIME DEFAULT CURRENT_TIMESTAMP,
    updated_at DATETIME DEFAULT CURRENT_TIMESTAMP
        ON UPDATE CURRENT_TIMESTAMP
);

6.3 Create products

CREATE TABLE products (
    product_id INT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
    product_name VARCHAR(120) NOT NULL,
    unit_price DECIMAL(10,2) NOT NULL,
    category VARCHAR(50),
    status ENUM('ACTIVE','INACTIVE') DEFAULT 'ACTIVE'
);

6.4 Create orders

CREATE TABLE orders (
    order_id BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
    customer_id INT UNSIGNED NOT NULL,
    order_date DATETIME DEFAULT CURRENT_TIMESTAMP,
    total_amount DECIMAL(12,2),
    status VARCHAR(20) DEFAULT 'NEW',
    CONSTRAINT fk_orders_customer
        FOREIGN KEY (customer_id)
        REFERENCES customers(customer_id)
);

6.5 Create order items

CREATE TABLE order_items (
    order_item_id BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
    order_id BIGINT UNSIGNED NOT NULL,
    product_id INT UNSIGNED NOT NULL,
    quantity INT NOT NULL,
    unit_price DECIMAL(10,2) NOT NULL,
    CONSTRAINT fk_items_order
        FOREIGN KEY (order_id)
        REFERENCES orders(order_id),
    CONSTRAINT fk_items_product
        FOREIGN KEY (product_id)
        REFERENCES products(product_id)
);

6.7 Add a view to make code conversion observable

CREATE VIEW customer_order_summary AS
SELECT
    c.customer_id,
    c.customer_name,
    COUNT(o.order_id) AS order_count,
    IFNULL(SUM(o.total_amount), 0) AS total_spend
FROM customers c
LEFT JOIN orders o
    ON c.customer_id = o.customer_id
GROUP BY c.customer_id, c.customer_name;
Why this schema? It contains unsigned integers, auto-increment columns, DECIMAL, TINYINT(1), DATETIME, an ENUM, an ON UPDATE clause, foreign keys and a view using MySQL-specific IFNULL(). These make the conversion easier to observe.

17. Step 12 — Observable conversion: MySQL → PostgreSQL

The examples below are expected/representative target forms for teaching the conversion concept. DMS may generate different but valid PostgreSQL syntax depending on the exact source definition, DMS version and conversion settings. Always treat the generated SQL in the DMS console as authoritative.

Example A — AUTO_INCREMENT + UNSIGNED

-- MySQL source
customer_id INT UNSIGNED
    AUTO_INCREMENT
    PRIMARY KEY

Expected PostgreSQL concept

-- Representative PostgreSQL form
customer_id INTEGER
    GENERATED BY DEFAULT AS IDENTITY
    PRIMARY KEY

Example B — DECIMAL

-- MySQL
credit_limit DECIMAL(12,2)

Expected PostgreSQL concept

-- PostgreSQL
credit_limit NUMERIC(12,2)

Example C — DATETIME

-- MySQL
created_at DATETIME
    DEFAULT CURRENT_TIMESTAMP

Expected PostgreSQL concept

-- PostgreSQL
created_at TIMESTAMP
    DEFAULT CURRENT_TIMESTAMP

Example D — Boolean-like flag

-- MySQL
is_active TINYINT(1)
    DEFAULT 1

Expected PostgreSQL concept

-- PostgreSQL concept
is_active BOOLEAN
    DEFAULT TRUE

Example E — ENUM

-- MySQL
status ENUM('ACTIVE','INACTIVE')
    DEFAULT 'ACTIVE'

Possible PostgreSQL representation

-- One possible target representation
CREATE TYPE product_status
AS ENUM ('ACTIVE','INACTIVE');

status product_status
    DEFAULT 'ACTIVE'

Example F — MySQL ON UPDATE

-- MySQL
updated_at DATETIME
    DEFAULT CURRENT_TIMESTAMP
    ON UPDATE CURRENT_TIMESTAMP

PostgreSQL consideration

-- PostgreSQL has no identical
-- column-level ON UPDATE clause.

-- A common manual design is:
-- BEFORE UPDATE trigger
-- that sets updated_at = CURRENT_TIMESTAMP

Example G — IFNULL()

-- MySQL view
IFNULL(SUM(o.total_amount), 0)
    AS total_spend

PostgreSQL equivalent concept

-- PostgreSQL
COALESCE(SUM(o.total_amount), 0)
    AS total_spend
Key observation: schema conversion is not simply “copy the CREATE TABLE statement.” It is an engine-to-engine translation problem involving data types, identity behavior, defaults, expressions, constraints and code objects.

19. Step 14 — Action-item exercise

Use the actual DMS Action items pane as the source of truth. The following exercise teaches how to turn an action item into a target-side design decision.

Exercise A — updated_at behavior

Source requirement: Every time a customer row is updated, updated_at should automatically become the current timestamp.

MySQL source:

updated_at DATETIME DEFAULT CURRENT_TIMESTAMP
    ON UPDATE CURRENT_TIMESTAMP

Question: If DMS flags the MySQL ON UPDATE behavior for manual action, how will you implement the equivalent behavior in PostgreSQL?

Exercise B — ENUM design

Source requirement: Product status must be either ACTIVE or INACTIVE.

Question: Review the generated target SQL. Decide whether the generated representation is acceptable. If not, choose between a PostgreSQL ENUM, a lookup table, or a CHECK constraint and justify the choice.

Exercise C — Validation

Before applying changes, identify three SQL queries that would prove the target structure satisfies the source requirements.

Suggested solution for Exercise A

One valid PostgreSQL implementation is a trigger:

CREATE OR REPLACE FUNCTION set_customer_updated_at()
RETURNS TRIGGER AS $$
BEGIN
    NEW.updated_at = CURRENT_TIMESTAMP;
    RETURN NEW;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER trg_customers_updated_at
BEFORE UPDATE ON customers
FOR EACH ROW
EXECUTE FUNCTION set_customer_updated_at();
This is a teaching example. Do not assume DMS will generate exactly this trigger. The exercise is about resolving the semantic gap identified during assessment/conversion.

Best practice: Do not blindly edit generated SQL just to make the action-item count disappear. The target implementation must preserve the intended business behavior.

21. Step 16 — Apply Changes

This is where the converted schema moves from the DMS migration project into the actual PostgreSQL target database.

Select target schema

In the target data provider pane, select the target schema/database node.

2

Apply changes

Choose Actions → Apply changes.

3

Confirm

Confirm the operation and monitor its progress.

4

22. Step 17 — Validate the PostgreSQL schema

22.1 List tables

\c saleslab_pg

SELECT table_schema, table_name
FROM information_schema.tables
WHERE table_schema NOT IN ('pg_catalog','information_schema')
ORDER BY table_schema, table_name;

22.2 Inspect columns and data types

SELECT
    table_schema,
    table_name,
    column_name,
    data_type,
    is_nullable,
    column_default
FROM information_schema.columns
WHERE table_schema NOT IN ('pg_catalog','information_schema')
ORDER BY table_schema, table_name, ordinal_position;

22.3 Check primary/foreign keys

SELECT
    tc.table_schema,
    tc.table_name,
    tc.constraint_name,
    tc.constraint_type
FROM information_schema.table_constraints tc
WHERE tc.table_schema NOT IN ('pg_catalog','information_schema')
ORDER BY tc.table_name, tc.constraint_type;

22.4 Check the view

SELECT table_schema, table_name, table_type
FROM information_schema.tables
WHERE table_name = 'customer_order_summary';

22.5 Validate identity/sequence behavior

SELECT
    table_name,
    column_name,
    column_default,
    is_identity
FROM information_schema.columns
WHERE table_schema = 'public'
  AND table_name IN
      ('customers','products','orders','order_items')
ORDER BY table_name, ordinal_position;

22.6 Functional validation

SELECT *
FROM customer_order_summary
ORDER BY customer_id;
Validation challenge: Compare the PostgreSQL result with the original MySQL result. The schema may be different syntactically, but the intended behavior should be equivalent.

26. Troubleshooting

Data Provider connection test fails

Check VPC/subnet routing, security group inbound rules on MySQL 3306 and PostgreSQL 5432, NACLs, DNS, database availability and the secret/IAM configuration.

Target schema cannot be created

For RDS PostgreSQL, verify the Schema Conversion user has the privileges required by AWS, including rds_superuser for the documented RDS target scenario.

Action item remains after conversion

This is not necessarily an error. It means DMS identified a construct requiring attention. Read the recommendation, decide the target implementation, edit the converted SQL where appropriate, and validate the semantics.

Target tables exist but have no rows

This is expected if you only performed Schema Conversion + Apply Changes. Use a separate AWS DMS data migration task to migrate the data.

Generated SQL differs from the examples in this lab

The examples are representative teaching examples. DMS-generated SQL is the authoritative output for your actual source definition, target version and conversion configuration.

28. Final mental model

Remember:

  • Data Provider = database connection/environment definition.
  • Migration Project = workspace connecting source, target, secrets and instance profile.
  • Assessment = identify conversion complexity and manual action items.
  • Conversion = generate target-compatible schema/code.
  • Review/Edit = resolve semantic differences and action items.
  • Apply Changes = create/update target schema and converted code.
  • DMS Replication Task = move the actual data.

        REFERENCES products(product_id)

FROM customers c

    ON c.customer_id = o.customer_id
GROUP BY c.customer_id, c.customer_name;
