Hands-On Lab: AWS DMS Data Provider & Schema Conversion

MySQL → PostgreSQL heterogeneous database migration lab. You will create source and target data providers, configure an instance profile and Secrets Manager credentials, create a migration project, run an assessment, convert a MySQL schema to PostgreSQL, review the converted SQL, and optionally apply it to the PostgreSQL target.

No OracleMySQL → PostgreSQLDMS Schema ConversionData ProvidersMigration ProjectHands-on
Important distinction: DMS Schema Conversion converts database schema and supported code objects; it does not migrate table data. AWS states that MySQL → PostgreSQL is a supported Schema Conversion path. After schema conversion, use AWS DMS data migration/replication to move the actual rows. citeturn0search5turn0search6

1. Lab Objectives

  • Understand what a Data Provider represents.
  • Create a MySQL source data provider.
  • Create a PostgreSQL target data provider.
  • Create an AWS DMS instance profile.
  • Store database credentials in AWS Secrets Manager.
  • Create a DMS migration project.
  • Run a conversion assessment.
  • Convert a MySQL schema into PostgreSQL-compatible schema/code.
  • Review conversion action items.
  • Apply the converted schema to PostgreSQL or export the generated SQL.
  • Understand how Schema Conversion connects to the later DMS data-migration task.

2. Lab Architecture

AWS describes the Schema Conversion workflow using three core resources: an instance profile, data providers, and a migration project. Database credentials are stored in Secrets Manager rather than in the data provider itself. citeturn0search6turn0search1

4. Prerequisites

  • AWS account with permissions to use AWS DMS, IAM, Secrets Manager and RDS.
  • A MySQL database reachable from the DMS Schema Conversion networking environment.
  • A PostgreSQL database reachable from the DMS Schema Conversion networking environment.
  • Preferably place both databases in the same VPC or configure the required routing/security rules.
  • Security groups must allow MySQL TCP/3306 and PostgreSQL TCP/5432 from the appropriate DMS networking source.
  • AWS DMS Schema Conversion requires appropriate network connectivity between DMS and the source/target databases. citeturn0search0

5. Create the MySQL Sample Database

Use the following small business schema. It deliberately includes common MySQL data types and objects so students can inspect how they are represented in PostgreSQL.

CREATE DATABASE saleslab;

USE saleslab;

CREATE TABLE customers (
    customer_id INT AUTO_INCREMENT PRIMARY KEY,
    customer_name VARCHAR(100) NOT NULL,
    email VARCHAR(150),
    credit_limit DECIMAL(12,2),
    is_active BOOLEAN DEFAULT TRUE,
    created_at DATETIME DEFAULT CURRENT_TIMESTAMP
);

CREATE TABLE products (
    product_id INT AUTO_INCREMENT PRIMARY KEY,
    product_name VARCHAR(120) NOT NULL,
    unit_price DECIMAL(10,2) NOT NULL,
    category VARCHAR(50)
);

CREATE TABLE orders (
    order_id BIGINT AUTO_INCREMENT PRIMARY KEY,
    customer_id INT NOT NULL,
    order_date DATETIME DEFAULT CURRENT_TIMESTAMP,
    total_amount DECIMAL(12,2),
    status VARCHAR(20) DEFAULT 'NEW',
    CONSTRAINT fk_orders_customer
        FOREIGN KEY (customer_id)
        REFERENCES customers(customer_id)
);

CREATE TABLE order_items (
    order_item_id BIGINT AUTO_INCREMENT PRIMARY KEY,
    order_id BIGINT NOT NULL,
    product_id INT NOT NULL,
    quantity INT NOT NULL,
    unit_price DECIMAL(10,2) NOT NULL,
    CONSTRAINT fk_items_order
        FOREIGN KEY (order_id)
        REFERENCES orders(order_id),
    CONSTRAINT fk_items_product
        FOREIGN KEY (product_id)
        REFERENCES products(product_id)
);

6. Create the PostgreSQL Target Database

Step 6.1 Create an Amazon RDS for PostgreSQL instance, or use an existing PostgreSQL instance.
Step 6.2 Create the target database:
CREATE DATABASE saleslab;
Step 6.3 Create a user for Schema Conversion and grant the privileges required by your target configuration.
-- Example only. Use your organization's password policy.
CREATE USER dms_sc_user WITH PASSWORD 'ChangeMe_StrongPassword';

GRANT CONNECT ON DATABASE saleslab TO dms_sc_user;
GRANT CREATE ON DATABASE saleslab TO dms_sc_user;

AWS documents CONNECT and CREATE on the target database as minimum privileges for PostgreSQL Schema Conversion; RDS for PostgreSQL has additional role requirements documented by AWS. citeturn0search8

7. Store Database Credentials in AWS Secrets Manager

DMS Schema Conversion uses Secrets Manager for database credentials. AWS's migration-project workflow associates a secret and IAM role with each data provider. citeturn0search13

7.1 MySQL Secret

{
  "username": "dms_sc_user",
  "password": "YOUR_MYSQL_PASSWORD",
  "engine": "mysql",
  "host": "YOUR_MYSQL_ENDPOINT",
  "port": 3306,
  "dbname": "saleslab"
}

7.2 PostgreSQL Secret

{
  "username": "dms_sc_user",
  "password": "YOUR_POSTGRES_PASSWORD",
  "engine": "postgres",
  "host": "YOUR_POSTGRES_ENDPOINT",
  "port": 5432,
  "dbname": "saleslab"
}
Console: AWS Console → Secrets Manager → Store a new secret → Other type of secret → enter the database credentials → give clear names such as dms-lab/mysql and dms-lab/postgres.

8. Create the DMS Schema Conversion Instance Profile

The instance profile supplies the network and security settings that DMS Schema Conversion uses to connect to the databases and protect conversion data. citeturn0search6

Step 8.1 Open AWS DMS → Instance profiles.
Step 8.2 Choose Create instance profile.
Step 8.3 Name it lab-dms-sc-profile.
Step 8.4 Select the VPC containing the database instances.
Step 8.5 Select appropriate subnets and security group(s).
Step 8.6 Configure encryption/security settings according to the lab environment.
Step 8.7 Create the instance profile.
For a training environment, keeping MySQL, PostgreSQL and the DMS networking components in one VPC can make routing and security-group troubleshooting substantially easier.

9. Create the MySQL Source Data Provider

AWS supports MySQL as a source data provider for DMS Schema Conversion, with PostgreSQL as a supported target. AWS documents MySQL source privileges including SELECT ON *.* and SHOW VIEW ON *.*. citeturn0search5

Step 9.1 Open AWS DMS → Data providers → Create data provider.
Step 9.2 Name: lab-mysql-source.
Step 9.3 Purpose: Schema Conversion.
Step 9.4 Engine type: MySQL.
Step 9.5 Enter the MySQL server name, port 3306, and database name saleslab.
Step 9.6 Configure SSL according to the lab requirement.
Step 9.7 Create the data provider.
Do not put the database password into the data provider. AWS documents that credentials are stored separately in Secrets Manager and associated with the migration project. citeturn0search1

10. Create the PostgreSQL Target Data Provider

Step 10.1 Choose Data providers → Create data provider.
Step 10.2 Name: lab-postgres-target.
Step 10.3 Purpose: Schema Conversion.
Step 10.4 Engine type: PostgreSQL.
Step 10.5 Enter the PostgreSQL server name, port 5432, and database saleslab.
Step 10.6 Create the data provider.

AWS supports PostgreSQL as a target for DMS Schema Conversion. citeturn0search11turn0search8

11. Create IAM Access for Secrets Manager

The migration project needs an IAM role that allows DMS to retrieve the database credentials from Secrets Manager. The exact managed/custom permissions should follow the current AWS DMS Schema Conversion setup for your account and Region.

Conceptually:

       +---- Source Secret
       |

       v
IAM Role
       |
       +---- secretsmanager:GetSecretValue
       +---- required KMS decrypt permission

Use a dedicated role and scope secret/KMS permissions to the specific lab secrets rather than granting unrestricted access to every secret in the account.

12. Create the Migration Project

Step 12.1 Open AWS DMS → Migration projects → Create migration project.
Step 12.2 Name: mysql-to-postgres-lab.
Step 12.3 Select instance profile: lab-dms-sc-profile.
Step 12.4 Source: lab-mysql-source.
Step 12.5 Select the MySQL Secrets Manager secret and its IAM role.
Step 12.6 Target: lab-postgres-target.
Step 12.7 Select the PostgreSQL Secrets Manager secret and its IAM role.
Step 12.8 Create the migration project.

AWS's documented workflow is to create a migration project using the source data provider, target data provider, instance profile and Secrets Manager credentials. citeturn0search13

15. Convert the MySQL Schema

Step 15.1 In the migration project, choose the MySQL source schema.
Step 15.2 Start Convert.
Step 15.3 Wait for conversion to complete.
Step 15.4 Inspect tables, views, routines and other supported objects.
Step 15.5 Compare source and converted SQL.

AWS states that Schema Conversion creates a local version of converted database objects, which can be reviewed, edited, applied to the target, or saved/exported as SQL. citeturn0search3

16. What Should Students Look For?

MySQL SourceWhat to Observe in PostgreSQL Conversion
AUTO_INCREMENTPostgreSQL-compatible identity/sequence representation.
DATETIMEPostgreSQL timestamp-compatible representation.
DECIMALPostgreSQL numeric-compatible representation.
BOOLEANPostgreSQL boolean representation.
Foreign keysEquivalent PostgreSQL constraints where supported.
Views/routinesInspect converted SQL and action items carefully.
The exact generated SQL depends on the source objects, database versions, conversion settings and AWS DMS conversion engine. Treat the table above as an observation checklist, not as a promise of exact generated syntax.

17. Apply the Converted Schema

You have two useful training options:

Option A — Apply

Use DMS Schema Conversion to apply the converted code directly to the PostgreSQL target.

Option B — Export

Save/export the converted SQL, inspect it, make manual changes if required, then execute it against PostgreSQL.

AWS supports both applying converted code to the target and exporting converted code for review/editing. citeturn0search3turn0search6

Recommended classroom exercise: Export the generated SQL first. Ask students to identify three MySQL-to-PostgreSQL differences before applying the schema.

18. Validate the PostgreSQL Schema

Connect to PostgreSQL and run:

\c saleslab

\dt

\d customers
\d products
\d orders
\d order_items

Check that the expected tables and constraints exist.

SELECT table_name
FROM information_schema.tables
WHERE table_schema = 'public'
ORDER BY table_name;
Remember: At this point you have converted/applied the schema. The data rows are not automatically migrated just because Schema Conversion completed.

21. Validation Exercise

MySQL

SELECT COUNT(*) FROM customers;
SELECT COUNT(*) FROM products;
SELECT COUNT(*) FROM orders;
SELECT COUNT(*) FROM order_items;

PostgreSQL

SELECT COUNT(*) FROM customers;
SELECT COUNT(*) FROM products;
SELECT COUNT(*) FROM orders;
SELECT COUNT(*) FROM order_items;

Compare the counts and then validate a few business queries:

SELECT
    c.customer_name,
    COUNT(o.order_id) AS order_count,
    COALESCE(SUM(o.total_amount),0) AS total_value
FROM customers c
LEFT JOIN orders o
    ON c.customer_id = o.customer_id
GROUP BY c.customer_name
ORDER BY c.customer_name;
