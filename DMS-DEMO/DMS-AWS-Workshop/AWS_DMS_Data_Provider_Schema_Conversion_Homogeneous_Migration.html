AWS DMS: Data Providers, Schema Conversion & Homogeneous Data Migrations

A practical conceptual guide explaining where Data Providers fit, what AWS DMS Schema Conversion does, what a homogeneous migration means, and how these capabilities relate to the traditional DMS endpoint → replication instance → replication task workflow.

AWS DMSData ProviderSchema ConversionHomogeneous MigrationHeterogeneous Migration
Key idea: Think of Data Provider as the database environment/connection definition used by DMS migration tooling, Schema Conversion as the structure/code translation step for engine differences, and Data Migration as moving the actual data.

1. Three Concepts at a Glance

Data Provider

Represents a database environment that can participate in a DMS migration workflow. It captures information about where the database is and how it can be accessed.

Think: “Where is my database?”

Schema Conversion

Converts supported schema objects and database code from a source database engine to the target database engine.

Think: “How does the structure translate?”

Homogeneous Migration

Moves data between databases using the same database engine, such as PostgreSQL → PostgreSQL.

Think: “Same engine, move the data.”

2. Where Data Provider Fits

A Data Provider is different from the traditional DMS replication task. A replication task performs the actual replication/migration operation between configured endpoints.

5. What is Schema Conversion?

Schema Conversion addresses the structural and database-code differences that arise when the source and target database engines are different.

Important: Schema Conversion is not the same thing as copying table rows. It focuses on supported schema objects and database code; DMS data migration handles the movement of data.

6. Example: Oracle → PostgreSQL

Source schema

CREATE TABLE CUSTOMER (
    CUSTOMER_ID NUMBER(10),
    CUSTOMER_NAME VARCHAR2(100),
    CREATED_DATE DATE
);

Conceptual target representation

CREATE TABLE CUSTOMER (
    CUSTOMER_ID NUMERIC(10),
    CUSTOMER_NAME VARCHAR(100),
    CREATED_DATE TIMESTAMP
);

In a heterogeneous migration, the target representation may need changes because Oracle and PostgreSQL have different data types and SQL/database features. Schema Conversion helps automate supported translations, but conversion output should be reviewed and tested before production use.

12. Common Misunderstandings

“Data Provider is the same as Endpoint.”
Not necessarily. They serve different roles in DMS migration workflows. Endpoints are the traditional source/target connection objects used by replication tasks.
“Schema Conversion migrates the data.”
Schema Conversion is focused on converting supported schema/database objects and code. Data migration is the movement of the actual data.
“Homogeneous means no DMS is required.”
Not true. DMS can still be used to perform homogeneous data migrations.
“Heterogeneous migration is only a schema problem.”
It can involve schema, data types, SQL/database code, compatibility, validation, and operational considerations.

13. Suggested Training Flow

  1. Explain the difference between database, data provider, endpoint, replication instance, and replication task.
  2. Demonstrate PostgreSQL → PostgreSQL as a homogeneous migration.
  3. Explain why Oracle → PostgreSQL is heterogeneous.
  4. Introduce Schema Conversion using a simple table/data-type example.
  5. Show the target schema produced/adjusted after conversion.
  6. Use DMS to perform the actual data migration.
  7. Validate row counts and data quality.
  8. Finally automate starting the DMS task using Lambda, as a separate orchestration step.
